# ADR 0007：多營運中心（多工廠）的資料架構

- 狀態：**已採用修訂版（Key User，2026-11-03，依草稿確認）**：營運中心改為一廠一個 PostgreSQL schema，
  取代同日採用的第一版（單一 schema + `plant_id` + RLS，摘要見文末），並修訂 ADR 0001 §4、ADR 0006 §5。
  §6、§8、§9 依 2026-11-03 的回覆改寫（全部在同一個資料庫、拋轉設定由使用者維護、合併報表跨 schema 統計），同日依草稿確認。
  Q1–Q16 均已回覆或撤回
- 範圍：營運中心在 PostgreSQL 的定義方式、資料表分層、營運中心切換與隔離、migration、跨廠作業、法人層、集團主檔、
  多據點部署、轉檔
- 相關：ADR 0001 §4、ADR 0006 §5、`specs/features/aoo/plant_maintenance.feature`（aooi901，P1–P13）

## 背景

### TipTop 的做法

- 一個營運中心一個資料庫 schema。新增營運中心要先由 DBA 建 schema，aooi901 再登錄到 `azp_file`，
  azp03 記錄 schema 名稱（plant_maintenance.feature P1）。
- 每個 schema 都有自己一份業務表，包含主檔，例如料件主檔 `ima_file` 每廠一份，表上沒有營運中心欄位。
- 跨營運中心作業要用 `s_getdbs` / `s_dbstring` 由營運中心代碼取得 schema 名稱，再以 `schema.表` 存取
  （`tiptop/sub/4gl/s_getdbs.4gl:4-80`）；標準程式中有 282 個程式檔使用 `s_dbstring(`。
- 系統資料（程式、權限、使用者）在 `ds`，各營運中心 schema 怎麼取用要以正式區為準（見 p_zxw X9）。
- 主檔由「資料中心」拋轉到各廠：aooi600 集團中心、aooi602 拋轉原則（`gew_file`）、`gex_file` 拋轉記錄；
  資料類型 0 基本資料、1 料件、2 BOM、3 ECN、4 客戶、5 廠商、6 會計科目、7 價格。

### 公司的實際狀況（已回覆）

- Q1：每廠各為一個法人。
- Q2、Q6：主檔在各廠之間拋轉同步，拋轉設定由使用者維護。
- Q3、Q8：法規要求各廠（各法人）獨立；全部工廠放在同一個 PostgreSQL 資料庫，各廠有自己的 schema。
- Q4、Q8、Q9：財務合併報表需要跨廠，只要各期各科目餘額，由程式跨 schema 統計。

## 決策

### 1. 一廠一個 schema

| schema | 內容 | 例子 |
|---|---|---|
| 共用 schema（沿用現有的 `public`） | 系統資料、營運中心與法人、集團中心與拋轉設定 | 程式、權限、使用者、資料字典、`plant`、法人、拋轉規則 |
| 工廠 schema，每廠一個 | 該廠的交易、庫存、參數、工廠層主檔；表上**不帶** `plant_id` | `ds01.item`、`ds01.inventory_txn` |

- 每廠（每個法人）的資料實體上分開：可以單獨備份、還原（`pg_dump -n`），日後要移到別台伺服器時搬 schema 即可（§9）。
- 一個 Oracle schema 對一個 PostgreSQL schema，轉檔與新舊比對最直接。
- 工廠 schema 名稱為 `ds` 加兩位數字，例如 `ds01`（Q11），與營運中心代碼無關；記在營運中心的「資料庫代碼」
  （`plant.schema_name`，即 TipTop azp03，P13），建立後不可修改。兩位數最多 99 個工廠，不夠時再加位數。
- 名稱一律小寫：PostgreSQL 不加引號的識別字會自動轉成小寫，用大寫就得在每個 SQL 加雙引號（`"DS01"`），
  容易出錯。TipTop（Oracle）是轉成大寫，所以 Oracle 系統目錄裡看到的是 `DS01`，轉到 PostgreSQL 一律存 `ds01`。

### 2. 每張表都要決定層級

萃取時逐表決定，記在 legacy-map 的 `scope` 欄位，與逐欄對應一起審核：

| 層級 | 放在 | 帶 `plant_id` | 例子 |
|---|---|---|---|
| `system` 系統層 | 共用 schema | 否 | 程式、權限、使用者、資料字典 |
| `group` 集團層 | 共用 schema | 否 | 集團中心、拋轉規則與拋轉紀錄（§8） |
| `plant` 工廠層 | 各工廠 schema | 否（所在 schema 就是營運中心） | 交易、庫存、各廠的參數（TipTop 每個 schema 的 aza、sma 等參數檔）、主檔（含拋轉收到的，§8） |

共用 schema 裡需要參照營運中心的資料照舊帶 `plant_id` 並以外鍵指向 `plant`，例如使用者的預設營運中心、
可使用營運中心（`user_plant`）、拋轉規則的目標營運中心。

### 3. 切換營運中心與隔離

- 目前使用者帶目前營運中心（同 ADR 0006 §5：web 存 session，bearer 用戶端用 `X-TTRS-Plant` 標頭，
  每次檢查是否在可使用營運中心內；非多營運中心使用者固定為預設營運中心）。
- 每個 use case 一個交易，開頭：
  `SET LOCAL ROLE ttrs_ds01; SET LOCAL search_path = ds01`（共用 schema 的表要寫明 `public.`）。
  SQL 不寫 schema 名稱，仍符合 sqlx 只接受字面 SQL 的規定；這等於 TipTop 的切換資料庫。
- **每廠一個資料庫角色**（資料庫名稱加 schema 名稱，例如正式資料庫 `ttrs` 的 `ttrs_ds01`；角色是整台 PostgreSQL 共用的，
  名稱帶資料庫名稱，測試資料庫 `ttrs_test` 的角色才不會和正式區衝突）：只能存取自己的工廠 schema 與共用 schema。
  API 的連線角色 `ttrs_app` 是各廠角色的成員，本身不能直接存取工廠 schema。
  即使 search_path 設錯，也讀不到別廠的資料（取代第一版的 RLS）。
- 「今天」依營運中心的時區（P6）計算。

### 4. migration 分兩套

- `migrations/`：共用 schema，照舊由 sqlx 執行一次。
- `migrations/plant/`：工廠層的表，由 TTRS 自己的 migration 工具對**每個**工廠 schema 套用；
  每個 schema 有自己的套用紀錄（在該 schema 內的 `_sqlx_migrations`）。
- API 啟動時先套用共用 migration，再逐一套用各工廠 schema；任何一個工廠失敗就不啟動。
- 同樣只能新增、不可修改已存在的檔案（CLAUDE.md 規則）。

### 5. 新增與刪除營運中心（影響 aooi901）

- 新增營運中心：在共用 schema 新增 `plant`（含資料庫代碼），以資料庫代碼建立工廠 schema 與角色，
  套用全部工廠 migration（Q12：由系統自動建立）。回到 TipTop「營運中心就是 schema」，但不需要 DBA 手動建。
- 資料庫代碼預設為下一個未使用的號碼（Q14）。
- 刪除營運中心：沒有任何資料時（P10）才刪除工廠 schema 與角色。
- 執行建立 schema 的資料庫角色要有 `CREATE` 權限；只在新增、刪除營運中心時使用，平常的 API 連線不帶此權限。

### 6. 跨廠作業

- **財務合併報表（Q4、Q8、Q9）**：程式依使用者可使用的營運中心，在一個唯讀交易內逐一切換到各廠
  （`SET LOCAL ROLE`、`search_path`），用同一段 SQL 讀出各期各科目餘額，在程式中加總。
  SQL 仍是固定字串（符合 sqlx 的規定），不另建餘額表、不需要同步；傳票明細留在各廠的 schema。
- **其他跨廠查詢**（例如集團庫存查詢）也用同樣的方式逐廠讀取；不建跨 schema 的 view。
- **跨廠單據**（例如調撥）：同一個交易內依序切換兩廠的角色與 search_path 各寫一筆。逐一移植到該作業時再設計。

### 7. 法人層（Q1：每廠各為一個法人）

- 共用 schema 加法人主檔，`plant` 帶所屬法人（外鍵）。目前每廠各一個法人（1:1），結構仍允許日後一個法人有多個工廠。
- 法人資料來自 TipTop 的公司名稱資料檔 `zo_file`（每個營運中心 schema 各一份，以語言別為鍵）：
  公司對內／對外全名、簡稱（多語言，依 ADR 0005 另建 `_text` 表）、地址、電話、傳真、統一編號 zo06、
  稅籍號碼 zo11 等。移植公司資料維護時再逐欄萃取；轉檔時每個 schema 的 `zo_file` 成為該營運中心的法人。
- 會計、稅務以法人為單位。目前 1:1，會計資料放在各工廠 schema 即等於以法人分開
  （TipTop 也是每個 schema 各有自己的帳，如帳別參數檔 `aaa_file`）。

### 8. 主檔拋轉（Q2、Q6：各廠之間拋轉同步，拋轉設定由使用者維護）

- 照 TipTop：每廠的 schema 各存一份主檔（料件、BOM、ECN、客戶、廠商、會計科目、價格等），是工廠層的表。
- 移植 aooi600（集團中心）與 aooi602（拋轉設定，`gew_file`），讓使用者自己維護拋轉規則：
  資料中心、資料類型、拋轉營運中心、自動拋轉否、拋轉條件、子公司可否刪除、可否更新已存在資料、通知人員。
  拋轉設定與拋轉紀錄（`gex_file`）放在共用 schema（集團層）。
- 拋轉程式依規則把資料中心的資料複製到目標工廠：同一個資料庫內，在一個交易中依序切換到各目標廠寫入，
  結果寫入拋轉紀錄。自動拋轉在資料中心存檔時觸發，手動拋轉由作業執行（TipTop aoop605 等）。
- 各主檔作業的拋轉動作（例如 aimi100 的 carry）在移植該作業時一併處理；拋轉規則與程式另走萃取流程。

### 9. 部署（Q3、Q8：全部在同一個資料庫）

- 所有工廠 schema（`ds01`–`ds05`）與共用 schema 放在同一個 PostgreSQL 資料庫、同一套 TTRS。
  法規要求的「各廠獨立」以每廠（每個法人）自己的 schema 與資料庫角色達成（§1、§3）。
- 不做多據點同步。日後若真有工廠因法規必須放到別台伺服器：把它的 schema 搬過去，總部以 `postgres_fdw`
  （PostgreSQL 版的 DB link，作用同 TipTop azp04 的 Oracle DB link）讀取，合併報表與拋轉程式照常逐廠處理；
  屆時另行設計。

### 10. 效能與備份

- 大表（庫存異動、總帳分錄等）在各工廠 schema 內依日期 RANGE 分區，方便歸檔；分區要在建表時決定，
  萃取時依 Q5 的量級在 legacy-map 記錄 `partition`。
- 量級（Q5）：每廠每年交易 100 萬筆以上、保存 10 年以上，單一交易明細表每廠會累積千萬筆以上。
  因此交易明細類的表（庫存異動、總帳分錄、訂單與採購單身等每年預期百萬筆的表）建表時就依年度分區；
  主檔、參數與量少的表不分區。哪些表分區在萃取時記在 legacy-map 的 `partition`。
- 資料保存 10 年以上（Q5）：分區以年度為單位；10 年內的資料一律留在線上可查，不刪除。
  更早的年度可以整個分區移到較便宜的儲存空間（tablespace），仍可查詢；是否刪除另行決定。
- 報表在唯讀複本上跑；各廠角色設 `statement_timeout`。
- 備份：整個資料庫做時間點還原，另可依 schema 單獨備份與還原單一工廠。

### 11. TipTop 轉檔

- 每個 Oracle 營運中心 schema 轉入對應的工廠 schema（以 azp03 對應，P13），表照搬並改用英文名稱；
  主檔也照搬，各廠一份（同 TipTop）。
- 拋轉設定（`gew_file`）照搬，之後由使用者維護。
- `ds` 的系統資料轉入共用 schema。

## 對現有程式的影響（確認後處理）

- ADR 0001 §4（單一 schema + `plant_id`）、ADR 0006 §5（RLS）改為本 ADR 的做法。
- 料件 `item`、庫存異動 `inventory_txn` 目前在 `public` 並帶 `plant_id`，改為工廠層 migration（目前沒有正式資料）。
- infra 改為每個 use case 一個交易，開頭設定角色與 search_path；目前直接用連線池執行 SQL。
- 營運中心維護（aooi901）：資料庫代碼成為必填的工廠 schema 名稱（P13 改寫）；新增時建 schema 與角色、刪除時移除（P14 起）。
- PostgreSQL 版 BDD 要建立測試用的工廠 schema 與角色。
- 移植 aooi600、aooi602 拋轉設定與拋轉程式（另走萃取流程）。
- 不受影響：系統層的使用者、權限、程式、資料字典（本來就在共用 schema，不帶 `plant_id`），Authorizer。

## 實作順序（確認後）

1. 修訂 ADR 0001 §4、ADR 0006 §5；營運中心規格：資料庫代碼（P13 改為工廠 schema 名稱）、新增／刪除時建立與移除 schema。
2. migration 工具（共用＋工廠）、資料庫角色；infra 每個 use case 一個交易並設定角色與 search_path。
3. 料件、庫存異動改為工廠層 migration。
4. 營運中心切換：目前使用者帶營運中心、session 或標頭、可使用營運中心檢查。
5. PostgreSQL 版 BDD 建立測試工廠 schema，驗證隔離（設錯營運中心時讀不到別廠資料）。

進度（2026-11-03）：第 1–3 步完成——migrations/0016（`plant.schema_name`、建立／移除 schema 與角色的資料庫函式）、
`migrations/plant/`、`ttrs_infra::plant_schema`（啟動時與新增營運中心時套用工廠 migration、工廠交易）、
料件與庫存異動改在工廠 schema、營運中心 P13–P15。工廠交易目前以 repository 方法為單位（每次呼叫一個交易），
整個 use case 一個交易待需要跨多次寫入的作業時再做。第 4 步營運中心切換需要另寫規格（cl_user 營運中心切換）；
第 5 步的隔離驗證情境隨第 4 步一起寫。

主檔拋轉（aooi600、aooi602 與拋轉程式）在移植主檔作業時另走萃取流程。

## 附錄：第一版（2026-11-03 採用，已由本修訂取代）

單一資料庫、單一 schema，業務表帶 `plant_id`，以 RLS（`current_setting('ttrs.plant_id')`）隔離；
